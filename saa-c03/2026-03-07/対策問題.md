## ネットワーク・接続（最頻出の弱点）

### 問題1（VPCエンドポイント）

ある企業は、プライベートサブネット内のEC2インスタンスからS3バケットへ大量のログデータをアップロードしている。現在はNATゲートウェイを経由しているが、月々のデータ転送コストが予算を超過している。S3へのアクセス要件は変えずに、コストを最小限に抑えるソリューションはどれか。

1. NATゲートウェイをNATインスタンスに置き換え、小さいインスタンスタイプを使用する
2. S3バケットへのゲートウェイ型VPCエンドポイントを作成し、ルートテーブルにエンドポイントへのルートを追加する
3. インターフェイス型VPCエンドポイントを作成し、プライベートDNSを有効にしてS3にアクセスする
4. EC2インスタンスをパブリックサブネットに移動し、インターネットゲートウェイ経由でS3にアクセスする

<details>
<summary>正解と解説</summary>

**正解: 2**

- **ゲートウェイ型VPCエンドポイント**はS3とDynamoDB向けに提供されており、**利用料金が無料**
- NATゲートウェイは処理データ量に応じた料金が発生するため、大量データ転送ではコストが高くなる
- インターフェイス型VPCエンドポイント（選択肢3）もS3に対応するが、時間課金+データ処理課金が発生するためゲートウェイ型より高コスト
- ゲートウェイ型はルートテーブルにエントリを追加する形で動作する

**覚えるポイント:** S3/DynamoDBへのアクセスコスト削減 → ゲートウェイ型VPCエンドポイント（無料）
</details>

### 問題2（CIDR重複時の接続）

2つの異なるAWSアカウントがそれぞれVPCを持っており、両方のVPCのCIDRブロックは`10.0.0.0/16`で重複している。アカウントAのEC2インスタンスから、アカウントBのVPC内にあるRDS PostgreSQLデータベースにプライベート接続でアクセスする必要がある。インターネットを経由せずにこの要件を満たすソリューションはどれか。

1. 2つのVPC間にVPCピアリング接続を確立する
2. Transit Gatewayを作成し、両方のVPCをアタッチする
3. アカウントBでRDSの前段にNLBを配置し、AWS PrivateLinkを使用してアカウントAからアクセスする
4. アカウントBのRDSでパブリックアクセスを有効にし、セキュリティグループでアカウントAのIPアドレスのみ許可する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **VPCピアリング**と**Transit Gateway**はCIDRブロックが重複するVPC間では使用不可
- **AWS PrivateLink**はCIDRの重複に関係なく接続可能。NLBを介してサービスを公開する仕組み
- 選択肢4はインターネット経由となりセキュリティ要件を満たさない

**覚えるポイント:** CIDRが重複 → VPCピアリング/TGW不可 → PrivateLink（NLB必須）
</details>

### 問題3（Route 53 Resolver）

ある企業は、オンプレミスのデータセンターとAWS VPCをDirect Connectで接続している。オンプレミスのアプリケーションが、VPC内のプライベートホストゾーンに登録されたDNS名を使用してEC2インスタンスにアクセスする必要がある。オンプレミスのDNSサーバーからVPC内のプライベートDNS名を解決するためのソリューションはどれか。

1. VPC内にカスタムDNSサーバーをEC2上に構築し、オンプレミスのDNSサーバーからフォワードする
2. Route 53 Resolverのアウトバウンドエンドポイントを作成し、オンプレミスのDNSサーバーにクエリを転送する
3. Route 53 Resolverのインバウンドエンドポイントを作成し、オンプレミスのDNSサーバーからこのエンドポイントにクエリを転送する
4. VPCのDHCPオプションセットを変更して、オンプレミスのDNSサーバーをVPCのDNSサーバーとして設定する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **Route 53 Resolver インバウンドエンドポイント**: オンプレミス → AWSへのDNSクエリ転送
- **Route 53 Resolver アウトバウンドエンドポイント**: AWS → オンプレミスへのDNSクエリ転送
- 選択肢1は動作するが、カスタムDNSサーバーの運用負荷が発生するためマネージドサービスが適切
- 選択肢4はVPC内のDNS解決に影響を与え、問題の解決にならない

**覚えるポイント:**
- オンプレ → AWS のDNS解決 = **インバウンド**エンドポイント
- AWS → オンプレ のDNS解決 = **アウトバウンド**エンドポイント
</details>

### 問題4（Network Firewall）

ある企業のプライベートサブネット内のEC2インスタンスが、特定の外部SaaS APIドメイン（例: `api.example.com`）のみと通信する必要がある。その他のインターネットへのアウトバウンド通信はすべてブロックしたい。この要件を満たすソリューションはどれか。

1. セキュリティグループのアウトバウンドルールで、`api.example.com`のIPアドレスのみを許可する
2. ネットワークACLで、`api.example.com`のIPアドレスへのアウトバウンド通信のみ許可する
3. AWS Network Firewallを構成し、`api.example.com`へのアウトバウンド通信のみ許可するドメインフィルタリングルールを設定する
4. AWS WAFを使用して、`api.example.com`以外のすべての通信をブロックするルールを作成する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **セキュリティグループ**と**ネットワークACL**はIPアドレスとポートでのフィルタリングのみ。ドメイン名（FQDN）ベースのフィルタリングは不可。SaaS APIのIPが変わる可能性もある
- **AWS Network Firewall**はドメイン名（FQDN）ベースのフィルタリングが可能
- **AWS WAF**はHTTP/HTTPSレイヤーの保護であり、ネットワークレベルのアウトバウンド制御には使えない

**覚えるポイント:** ドメイン名ベースのフィルタリング → AWS Network Firewall（SGやNACLではIPのみ）
</details>

### 問題5（API Gateway VPCリンク）

ある企業が、プライベートサブネット内のEC2インスタンスで動作するバックエンドAPIを外部に公開したい。セキュリティポリシーにより、APIリクエストがインターネットを経由してバックエンドに到達することは許可されていない。Amazon API Gatewayを使用してこの要件を満たすソリューションはどれか。

1. API Gatewayのリージョナルエンドポイントを作成し、NATゲートウェイ経由でプライベートサブネットのEC2にルーティングする
2. API GatewayのプライベートAPIを作成し、VPCエンドポイント経由でのみアクセスを許可する
3. API GatewayでREST APIを作成し、VPCリンクを構成してプライベートサブネットのNLB経由でEC2にアクセスする
4. API Gatewayのエッジ最適化エンドポイントを作成し、セキュリティグループでEC2へのアクセスを制限する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **VPCリンク**はAPI Gatewayからプライベートサブネット内のリソースに、インターネットを経由せずにアクセスするための機能
- REST APIのVPCリンクはNLBと連携し、HTTP APIのVPCリンクはALB/NLB/Cloud Mapと連携
- 選択肢2のプライベートAPIは、VPC内部からのみAPI Gatewayにアクセスする場合に使用するもので、外部公開の要件と矛盾する

**覚えるポイント:** API Gateway → プライベートサブネット = VPCリンク（NLB連携）
</details>

### 問題6（VPN冗長化）

ある企業は、オンプレミスのデータセンターとAWS VPCをAWS Site-to-Site VPNで接続している。オンプレミス側には1台のカスタマーゲートウェイデバイスが設置されている。AWS側の仮想プライベートゲートウェイには2本のVPNトンネルが構成されている。この構成における単一障害点を排除するために、最も適切な対策はどれか。

1. VPNトンネルの数を4本に増やす
2. 仮想プライベートゲートウェイを追加でもう1つ作成する
3. オンプレミスに2台目のカスタマーゲートウェイデバイスを追加し、2つ目のVPN接続を作成する
4. Direct Connect接続を追加し、VPN接続を削除する

<details>
<summary>正解と解説</summary>

**正解: 3**

- AWSのSite-to-Site VPNは、1つのVPN接続に対してデフォルトで**2本のトンネル**を提供しており、AWS側は冗長化されている
- **単一障害点はオンプレミス側のカスタマーゲートウェイデバイスが1台**であること
- 2台目のカスタマーゲートウェイデバイスを追加し、2つ目のVPN接続を作成することで完全な冗長化を実現

**覚えるポイント:** VPN冗長化の問題 → AWS側は既にトンネル2本で冗長 → 単一障害点はオンプレ側のカスタマーGW
</details>

### 問題7（Direct Connectのデータ転送コスト）

ある企業はオンプレミスのデータセンターとAWS間でDirect Connect接続を保有している。EC2インスタンスで生成された約1TBのレポートデータを毎月社員に配布する必要がある。社員はオンプレミスネットワーク内から配布データにアクセスする。データ転送コストを最小化する方法はどれか。

1. S3にデータを保存し、社員がインターネット経由でS3から直接ダウンロードする
2. EC2インスタンスから直接インターネット経由で社員にデータを配信する
3. Direct Connect経由でオンプレミスのファイルサーバーにデータを転送し、社員はローカルからアクセスする
4. CloudFrontを使用してS3のデータを配信し、社員がインターネット経由でアクセスする

<details>
<summary>正解と解説</summary>

**正解: 3**

- **Direct Connectのデータ転送料金**はインターネット経由のデータ転送より安い
- S3からインターネット経由でダウンロードする場合、S3のデータ転送アウト料金が発生する
- Direct Connect経由でオンプレに転送すれば、DC料金のみで済み、社員はローカルネットワーク内でアクセスするため追加の転送コストは不要

**覚えるポイント:** データ転送コスト: Direct Connect < インターネット。社員がオンプレにいるなら、DCでオンプレに持っていくのが最安
</details>

### 問題8（RAM + VPCピアリング）

2つの異なるAWSアカウントがそれぞれVPCを保有している。アカウントAのアプリケーションがアカウントBのALB背後のアプリケーションに頻繁にアクセスしており、NATゲートウェイ経由のデータ転送コストが問題になっている。データ転送コストを削減する方法の組み合わせとして適切なものはどれか。（2つ選択）

1. AWS Direct Connectで2つのアカウントを接続する
2. 2つのVPCをVPCピアリングで接続する
3. AWS Resource Access Manager（RAM）でVPCサブネットを共有する
4. AWS PrivateLinkで接続する
5. Transit Gatewayで2つのVPCを接続する

<details>
<summary>正解と解説</summary>

**正解: 2, 3**

- **VPCピアリング**: NATゲートウェイを経由せずにVPC間で直接通信でき、NAT GWの処理料金を削減
- **AWS RAM**: VPCサブネットを共有することで、異なるアカウントのリソースが同じVPC内に配置され、クロスAZ・クロスVPCのデータ転送コストを削減
- PrivateLinkも接続可能だが、NLBの料金やPrivateLinkのデータ処理料金が発生するため、VPCピアリングの方がコスト効率が良い
- Transit Gatewayは利用料金が発生し、2VPC間ではコスト面でVPCピアリングが有利

**覚えるポイント:** クロスアカウントのコスト削減 → VPCピアリング（無料） + RAM（サブネット共有で転送コスト削減）
</details>

### 問題9（SSM Run Command vs Patch Manager）

ある企業は、開発チームが管理する200台のEC2インスタンスに対して、特定のモニタリングソフトウェアを一括でインストールしたい。インスタンスはすべてSSMエージェントが導入済みで、Systems Managerで管理されている。最も効率的な方法はどれか。

1. AWS Systems Manager Patch Managerを使用して、カスタムパッチとしてソフトウェアをインストールする
2. AWS Systems Manager Run Commandを使用して、すべてのインスタンスでインストールコマンドを実行する
3. AWS CodeDeployを使用して、ソフトウェアを全インスタンスにデプロイする
4. 各インスタンスにSSH接続して手動でインストールする

<details>
<summary>正解と解説</summary>

**正解: 2**

- **Run Command**: 複数のEC2インスタンスに対して任意のコマンドやスクリプトを一括実行する機能。ソフトウェアのインストールに最適
- **Patch Manager**: OSやアプリケーションのセキュリティパッチの適用に特化した機能。任意のソフトウェアインストールには向かない
- CodeDeployはアプリケーションデプロイに特化しており、システムソフトウェアのインストールにはやや過剰

**覚えるポイント:**
- Run Command = 任意のコマンド/スクリプトの一括実行
- Patch Manager = セキュリティパッチの適用管理
</details>

### 問題10（Transfer Family）

ある企業はSFTPサーバーを使用して、取引先からのデータファイルを受信している。このSFTPベースのワークフローをAWSに移行し、受信データをS3に保存したい。取引先は既存のSFTPクライアントツールとワークフローを変更したくないと考えている。運用オーバーヘッドを最小限に抑えるソリューションはどれか。

1. EC2インスタンス上にオープンソースのSFTPサーバーを構築し、S3にデータを転送するスクリプトを作成する
2. AWS Transfer Familyを使用してSFTPサーバーを構成し、ストレージとしてS3を指定する
3. AWS DataSyncを使用して、オンプレミスのSFTPサーバーからS3へデータを同期する
4. AWS Storage Gatewayのファイルゲートウェイを使用して、NFSインターフェースでS3にデータを保存する

<details>
<summary>正解と解説</summary>

**正解: 2**

- **AWS Transfer Family**: SFTP/FTPS/FTPプロトコルに対応したフルマネージドのファイル転送サービス。S3やEFSをストレージとして使用可能
- 取引先は既存のSFTPクライアントをそのまま使用でき、接続先をAWS Transfer Familyのエンドポイントに変更するだけ
- **DataSync**: データの移行や同期に使うサービスであり、SFTPサーバーの代替にはならない
- Storage Gatewayはオンプレミスとのハイブリッドストレージ用

**覚えるポイント:**
- SFTPサーバーの移行・代替 → AWS Transfer Family
- データの同期・移行 → AWS DataSync
</details>

### 問題11（Elastic Beanstalk）

ある企業が、IIS上で動作するASP.NET Webアプリケーションを運用している。このアプリケーションをAWSに移行する際に、高可用性とスケーラビリティを確保しつつ、インフラ管理の負荷を最小限に抑えたい。最も適切なソリューションはどれか。

1. Amazon ECSでDockerコンテナとしてデプロイし、Fargateで実行する
2. EC2インスタンスにIISとASP.NETランタイムを手動でインストールし、ALBとAuto Scalingを構成する
3. AWS Elastic BeanstalkでWindows Server/.NETプラットフォームを選択してデプロイする
4. AWS LambdaでASP.NETアプリケーションを実行する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **Elastic Beanstalk**はIIS/.NETの組み合わせを**ネイティブサポート**しており、プラットフォームとして選択するだけでデプロイ可能
- ALB、Auto Scaling、ヘルスチェック等を自動で構成してくれるため、インフラ管理が最小限
- ECSでのコンテナ化は、アプリケーションのDocker化が必要で追加作業が発生する
- EC2手動構成は管理負荷が最も高い

**覚えるポイント:** IIS/.NET + 運用負荷最小 → Elastic Beanstalk（ネイティブサポートあり）
</details>

### 問題12（Transcribe / Comprehend / Macie）

ある医療機関が、録音された患者との面談音声をテキスト化してカルテシステムに入力したい。テキスト化の過程で、患者の氏名、住所、電話番号などの個人情報（PII）を自動的にマスキングしたい。最も適切なソリューションはどれか。

1. Amazon Pollyで音声をテキストに変換し、Amazon Comprehendで PIIを検出してマスキングする
2. Amazon Transcribeを使用し、PIIの識別とリダクション機能を有効にして音声をテキストに変換する
3. Amazon Translateで音声を処理し、Amazon Macieで出力テキストからPIIを検出する
4. Amazon Rekognitionで音声を分析し、個人情報に関連するキーワードを検出してマスキングする

<details>
<summary>正解と解説</summary>

**正解: 2**

- **Amazon Transcribe**: 音声→テキスト変換サービス。PII識別とリダクション（マスキング）機能を内蔵
- **Amazon Polly**: テキスト→音声変換（Transcribeの逆）
- **Amazon Translate**: テキストの言語翻訳サービス（音声処理機能なし）
- **Amazon Comprehend**: テキストの自然言語処理（感情分析、エンティティ抽出、PII検出）
- **Amazon Macie**: S3バケット内のデータからPIIを検出する専用サービス
- **Amazon Rekognition**: 画像・動画の分析サービス

**覚えるポイント（AI/MLサービスマップ）:**
| 目的 | サービス |
|------|---------|
| 音声→テキスト | Transcribe |
| テキスト→音声 | Polly |
| テキスト翻訳 | Translate |
| テキスト分析/PII検出 | Comprehend |
| S3内データのPII検出 | Macie |
| 画像/動画分析 | Rekognition |
| ドキュメント(PDF/画像)→テキスト | Textract |
</details>

### 問題13（Data Lifecycle Manager）

ある運用チームは、EC2インスタンスにアタッチされたEBSボリュームのバックアップを自動化したい。スナップショットを毎日取得し、14日間保持した後に自動的に削除する要件がある。運用負荷を最小限にする方法はどれか。

1. AWS Backupを使用してバックアップ計画を作成し、14日間のライフサイクルルールを設定する
2. CloudWatch Eventsで毎日Lambda関数をトリガーし、スナップショットの作成と古いスナップショットの削除を行う
3. Amazon Data Lifecycle Manager（DLM）でスナップショットライフサイクルポリシーを作成する
4. S3のライフサイクルポリシーで、14日を超えたスナップショットを自動削除する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **Data Lifecycle Manager（DLM）**: EBSスナップショットとAMIのライフサイクル管理に特化したサービス。スケジュールと保持期間を設定するだけで自動化可能
- AWS Backupも使えるが、DLMの方がEBSスナップショットに特化しておりシンプル
- 選択肢4は誤り: EBSスナップショットはS3に保存されるが、S3のライフサイクルポリシーでは管理できない（スナップショットはAWSが管理するS3領域に保存される）
- Lambda + CloudWatch Events は動作するが、DLMと比較して運用負荷が高い

**覚えるポイント:** EBSスナップショットの自動作成・保持・削除 → Data Lifecycle Manager（DLM）。S3ライフサイクルではスナップショットを管理できない
</details>

### 問題14（S3 Express One Zone）

ある企業は、機械学習推論アプリケーションを運用している。推論リクエストごとにS3上のモデルパラメータファイルを読み込む必要があり、1桁ミリ秒のレイテンシーでのデータ読み取りが要件である。最も適切なS3ストレージクラスはどれか。

1. S3 Standard
2. S3 Intelligent-Tiering
3. S3 Express One Zone
4. S3 One Zone-IA

<details>
<summary>正解と解説</summary>

**正解: 3**

- **S3 Express One Zone**: 1桁ミリ秒の一貫したデータアクセスレイテンシーを提供する最高性能のストレージクラス
- S3 Standard: 低レイテンシーだが、1桁ミリ秒は保証されない（通常は数十ミリ秒）
- S3 Intelligent-Tiering: コスト最適化が目的で、レイテンシー最適化ではない
- S3 One Zone-IA: 低頻度アクセス向けで、取得料金が発生する

**覚えるポイント:** 「1桁ミリ秒」「超低レイテンシー」がキーワード → S3 Express One Zone
</details>

### 問題15（Fargate vs EC2起動タイプ）

ある企業が、動画のリアルタイムエンコードを行うコンテナアプリケーションをAWS上にデプロイしたい。このアプリケーションはGPUを使用したハードウェアアクセラレーションが必須である。Amazon ECSでこのアプリケーションを実行する場合、最も適切な起動タイプはどれか。

1. Fargate起動タイプでGPU対応のタスク定義を作成する
2. GPU対応のEC2インスタンス（P系/G系）をECSクラスターに登録し、EC2起動タイプで実行する
3. Fargate Spotを使用してコストを最適化しながらGPU処理を実行する
4. AWS Batchを使用してFargate上でGPUジョブを実行する

<details>
<summary>正解と解説</summary>

**正解: 2**

- **FargateはGPUをサポートしていない**。GPUが必要な場合はEC2起動タイプを使用し、P系（推論/学習）やG系（グラフィックス）のGPU対応インスタンスが必要
- AWS BatchはGPU対応EC2インスタンスでの実行をサポートするが、Fargate上ではGPU不可

**覚えるポイント:** GPU必要 → Fargateは不可 → EC2起動タイプ（P系/G系インスタンス）
</details>

### 問題16（taskRoleArn vs executionRoleArn）

Amazon ECS上のコンテナアプリケーションが、実行中にDynamoDBテーブルからデータを読み取り、S3バケットにレポートを書き込む必要がある。このアプリケーションに最小権限でAWSリソースへのアクセスを許可する方法として正しいものはどれか。

1. ECSクラスターのコンテナインスタンスにアタッチされたIAMインスタンスプロファイルに、DynamoDBとS3のアクセス権限を付与する
2. ECSタスク定義の`executionRoleArn`に指定するIAMロールに、DynamoDBとS3のアクセス権限を付与する
3. ECSタスク定義の`taskRoleArn`に指定するIAMロールに、DynamoDBとS3のアクセス権限を付与する
4. ECSサービスにアタッチされたIAMサービスリンクロールに、DynamoDBとS3のアクセス権限を付与する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **taskRoleArn（タスクロール）**: コンテナ内のアプリケーションがAWSサービス（S3、DynamoDB等）にアクセスするための権限
- **executionRoleArn（タスク実行ロール）**: ECSエージェントがタスクを実行するために使用する権限（ECRからのイメージ取得、CloudWatch Logsへのログ送信など）
- インスタンスプロファイルへの権限付与は、そのインスタンス上のすべてのタスクに権限が付与されるため最小権限の原則に反する

**覚えるポイント:**
- **taskRoleArn**: アプリが使うAWSリソースへの権限（S3, DynamoDB等）
- **executionRoleArn**: ECS基盤がタスクを起動・実行するための権限（ECR, CloudWatch Logs等）
</details>

### 問題17（DocumentDB）

ある企業がオンプレミスでMongoDBを使用したアプリケーションを運用している。このアプリケーションをAWSに移行する際、MongoDBとの互換性を維持しつつ、データベースの運用管理をAWSに委任したい。最も適切なサービスはどれか。

1. Amazon RDS for MongoDB
2. Amazon DynamoDB
3. Amazon DocumentDB（MongoDB互換）
4. Amazon Neptune

<details>
<summary>正解と解説</summary>

**正解: 3**

- RDS for MongoDBは存在しない

### 問題18（クロスアカウントアクセス）

企業Aが、企業BのAWSアカウント内のS3バケットに保存されたデータを分析する必要がある。企業Bはセキュリティを維持しつつ、企業Aに読み取り専用アクセスを提供したい。最も安全で推奨される方法はどれか。

1. 企業BがIAMユーザーを作成し、アクセスキーとシークレットキーを企業Aに共有する
2. 企業BがS3バケットのACLを変更し、企業AのAWSアカウントIDに読み取り権限を付与する
3. 企業BがIAMロールを作成し、企業AのAWSアカウントがAssumeRoleできるように信頼ポリシーを設定する
4. 企業BがAmazon Cognitoユーザープールにユーザーを作成し、企業Aに認証情報を共有する

<details>
<summary>正解と解説</summary>

**正解: 3**

- **IAMロール + 信頼ポリシー（AssumeRole）** がクロスアカウントアクセスのAWSベストプラクティス
- IAMユーザーのアクセスキー共有は、長期的な認証情報の管理リスクがあり推奨されない
- S3 ACLは粗い粒度の制御しかできず、IAMポリシーほど柔軟でない
- Cognitoはエンドユーザー（モバイルアプリ、Webアプリのユーザー）向けの認証サービスであり、AWSアカウント間のアクセス制御には使わない

**覚えるポイント:**
- クロスアカウント → IAMロール + 信頼ポリシー（AssumeRole）
- Cognito → エンドユーザー認証用（アプリのログインなど）
</details>

### 問題19（Lambda実行ロールとリソースポリシー）

Lambda関数が、KMSカスタマーマネージドキーで暗号化されたSNSトピックにメッセージを発行する必要がある。必要な権限設定の正しい組み合わせはどれか。（3つ選択）

1. Lambda関数のリソースベースポリシーに、SNSへのPublish権限を付与する
2. Lambda実行ロールに、SNSへのPublish権限とKMSキーの使用権限を付与する
3. SNSトピックのアクセスポリシーで、Lambda実行ロールにPublish権限を付与する
4. KMSカスタマーマネージドキーのキーポリシーで、関連するプリンシパルにキー使用権限を付与する
5. KMSのAWSマネージドキーのキーポリシーを編集する
6. SNSトピックのアクセスポリシーで、Lambda関数のARNを直接指定してPublish権限を付与する

<details>
<summary>正解と解説</summary>

**正解: 2, 3, 4**

- **Lambda実行ロール（IDベースポリシー）**: Lambdaが他のサービスに**アクセスする側**なので、実行ロールに権限が必要。リソースベースポリシーはLambdaが**呼び出される側**の設定
- **SNSトピックのアクセスポリシー**: Lambda実行ロール（IAMロール）を指定して許可。Lambda関数のARNではなく、実行ロールのARNを指定する
- **KMSキーポリシー**: カスタマーマネージドキーのキーポリシーで利用者を許可。AWSマネージドキーはユーザーが編集できない

**覚えるポイント:**
- Lambdaが**アクセスする側** → 実行ロール（IDベースポリシー）
- Lambdaが**呼び出される側** → リソースベースポリシー
- KMS: カスタマーマネージドキー → キーポリシー編集可能、AWSマネージドキー → 編集不可
</details>

### 問題20（CloudFrontの活用）

あるグローバル企業が、ALB背後のEC2で動的コンテンツを生成し、S3に静的コンテンツを保存しているWebサイトを運営している。世界中のユーザーに対して両方のコンテンツを低遅延で配信したい。最もシンプルかつ効果的な方法はどれか。

1. 各リージョンにALB+EC2とS3バケットを配置し、Route 53のレイテンシールーティングでユーザーを最寄りのリージョンに誘導する
2. CloudFrontディストリビューションを作成し、ALBとS3バケットをそれぞれオリジンとして設定する。パスパターンに基づいてキャッシュビヘイビアを構成する
3. Global Acceleratorを使用して、ALBとS3をエンドポイントとして構成する
4. S3のクロスリージョンレプリケーションを有効にし、各リージョンのS3から直接コンテンツを配信する

<details>
<summary>正解と解説</summary>

**正解: 2**

- **CloudFront**は静的コンテンツと動的コンテンツの両方に対応。複数のオリジン（ALB、S3等）を設定し、パスパターンでルーティング可能
- 動的コンテンツもCloudFrontのエッジロケーション経由で高速化される（キャッシュだけでなく、AWSバックボーンネットワーク経由の通信最適化）
- マルチリージョン構成は管理コストが大幅に増加し、過剰な構成
- Global Acceleratorは固定IPやTCP/UDP最適化には有効だが、コンテンツキャッシュ機能はない

**覚えるポイント:** グローバル低遅延配信 → まずCloudFrontを検討。動的コンテンツにも有効（ALBをオリジンに設定）
</details>

### 問題21（CloudFront料金クラス）

スタートアップ企業が、米国と日本のユーザー向けに静的Webサイトを配信している。コストを最小限に抑えつつ、対象地域のユーザーに低遅延でコンテンツを届けたい。最も適切な構成はどれか。

1. 米国リージョンとアジアパシフィックリージョンにそれぞれS3バケットを配置し、Route 53のレイテンシールーティングで振り分ける
2. CloudFrontで全世界のエッジロケーションを使用する料金クラス（Price Class All）を設定する
3. CloudFrontで北米、ヨーロッパ、アジア、中東、アフリカのエッジロケーションを含む料金クラス（Price Class 200）を設定する
4. S3の静的Webホスティングを有効にし、CloudFrontを使用せずに直接配信する

<details>
<summary>正解と解説</summary>

**正解: 3**

- CloudFrontには3つの**料金クラス**がある:
  - **Price Class All**: 全エッジロケーション（最も高い）
  - **Price Class 200**: 北米、ヨーロッパ、アジア、中東、アフリカ（中間）
  - **Price Class 100**: 北米、ヨーロッパのみ（最も安い）
- 米国と日本がターゲットなので、Price Class 100では日本がカバーされない。Price Class 200が最適
- マルチリージョンS3+Route 53は管理が複雑でコスト増

**覚えるポイント:** CloudFrontの料金クラスで対象地域のみのエッジロケーションを使うことでコスト最適化
</details>

### 問題22（Compute Savings Plans）

ある企業は、EC2インスタンスとLambda関数を組み合わせたアプリケーションを1年以上運用する予定である。将来的にEC2からFargateへの移行も検討している。特定のインスタンスファミリーに縛られず、柔軟にコスト削減を実現する購入オプションはどれか。

1. EC2 Instance Savings Plans
2. Compute Savings Plans
3. スタンダードリザーブドインスタンス
4. コンバーティブルリザーブドインスタンス

<details>
<summary>正解と解説</summary>

**正解: 2**

| プラン | 適用範囲 | 柔軟性 |
|--------|---------|--------|
| EC2 Instance Savings Plans | 特定リージョンの特定インスタンスファミリー | 低い |
| Compute Savings Plans | **EC2 + Fargate + Lambda** | **最も高い** |
| スタンダードRI | 特定インスタンスタイプ | 最も低い |
| コンバーティブルRI | インスタンスタイプ変更可能だがEC2のみ | 中程度 |

- **Compute Savings Plans**はEC2、Fargate、Lambdaの全てに適用可能で、インスタンスファミリー、リージョン、OS、テナンシーの変更も自由
- EC2 Instance Savings Plansはインスタンスファミリーが固定されるため、将来の変更に対応しにくい

**覚えるポイント:** EC2 + Lambda + Fargate を横断してコスト削減 → Compute Savings Plans
</details>

### 問題23（RDS マルチAZ vs リードレプリカ）

ある企業のWebアプリケーションがRDS MySQLを使用している。データベース障害時に自動でフェイルオーバーし、RPO（目標復旧時点）を1秒未満にする必要がある。最も適切なソリューションはどれか。

1. RDS MySQLのリードレプリカを別のAZに配置する
2. RDS MySQLのマルチAZ配置を有効にする
3. RDS MySQLのスナップショットを5分ごとに取得するよう設定する
4. Amazon Aurora MySQLに移行し、リードレプリカを追加する

<details>
<summary>正解と解説</summary>

**正解: 2**

| 機能 | マルチAZ | リードレプリカ |
|------|---------|--------------|
| 目的 | **高可用性（HA）** | 読み取りスケーリング |
| レプリケーション | **同期** | 非同期 |
| 自動フェイルオーバー | **あり** | なし |
| RPO | **ほぼゼロ** | 数秒～数分の遅延あり |
| 読み取りクエリ | 不可（スタンバイ） | 可能 |

- マルチAZは同期レプリケーションにより、RPOをほぼゼロにできる
- リードレプリカは非同期レプリケーションのため、データの遅延が発生し、RPO 1秒未満を保証できない

**覚えるポイント:**
- 高可用性・自動フェイルオーバー・RPO最小 → マルチAZ
- 読み取りパフォーマンス向上 → リードレプリカ
</details>

### 問題24（Auto Scaling ポリシー）

ある企業の社内システムは、平日9:00～18:00にトラフィックが集中し、土日は利用されない。Auto Scalingグループでコスト効率よくパフォーマンスを維持する方法の組み合わせとして適切なものはどれか。（2つ選択）

1. Auto Scalingのライフサイクルフックを使用して、土日にインスタンスを終了する
2. スケジュールに基づくスケーリングを設定し、土日は最小・最大・希望容量を0にする
3. ターゲット追跡スケーリングポリシーを使用し、CPU使用率に基づいてスケーリングする
4. ステップスケーリングポリシーで、CloudWatchアラームに基づいてインスタンスを追加する
5. 予測スケーリングを使用して、過去のパターンに基づいてキャパシティを自動調整する

<details>
<summary>正解と解説</summary>

**正解: 2, 3**

- **スケジュールスケーリング**: 予測可能なトラフィックパターン（平日/休日）に基づいてキャパシティを調整。土日に容量を0にすることでコスト削減
- **ターゲット追跡スケーリング**: メトリクス（CPU使用率等）の目標値を設定し、自動でインスタンス数を調整。業務時間中のパフォーマンス維持に最適
- **ライフサイクルフック**: インスタンスの起動/終了時にカスタムアクションを実行する機能（ログ退避、設定処理等）であり、スケーリングポリシーではない

**覚えるポイント:** ライフサイクルフック ≠ スケーリングポリシー。フックは起動/終了時の処理用
</details>

### 問題25（EFS vs その他ストレージ）

複数のEC2インスタンスが共有する長期保存データと、各インスタンスが独立して使用する一時的な高速データ処理領域が必要である。Linuxベースの環境で、両方の要件を満たすストレージの組み合わせとして適切なものはどれか。（2つ選択）

1. 長期データ: 各EC2にEBSボリュームをアタッチ
2. 長期データ: Amazon EFSリージョンファイルシステム
3. 長期データ: AWS Storage Gatewayボリュームゲートウェイ
4. 一時データ: Amazon ElastiCache for Memcached
5. 一時データ: EC2インスタンスストア

<details>
<summary>正解と解説</summary>

**正解: 2, 5**

- **EFS**: 複数のEC2インスタンスから同時にマウント・アクセス可能な共有ファイルシステム。リージョンファイルシステムは複数AZで高可用性
- **インスタンスストア**: EC2インスタンスに物理的に接続された高速なストレージ。一時データに最適だが、インスタンス停止で消失する
- EBSは基本的に1つのEC2インスタンスにしかアタッチできない（Multi-Attach対応のio1/io2を除く）
- Storage Gatewayはオンプレミスとのハイブリッド構成向けで、EC2間の共有ストレージとしては過剰

**覚えるポイント:**
- 複数EC2で共有 + 永続化 → EFS
- 高速 + 一時的 → インスタンスストア
- 単一EC2 + 永続化 → EBS
</details>

### 問題26（Macie + EventBridge）

ある企業は、DynamoDBに保存された顧客データを毎月S3にエクスポートし、PIIの有無をスキャンしたい。PIIが検出された場合、コンプライアンスチームにメール通知したい。最も適切なソリューションの組み合わせはどれか。（2つ選択）

1. DynamoDBのエクスポート機能でS3に月次出力し、Macieの分類ジョブでスキャンする
2. DynamoDB Streamsでレコード変更をキャプチャし、Lambda+Comprehendで各レコードのPIIを検出する
3. Macieのジョブ完了イベントをEventBridgeで捕捉し、SNS経由でメール通知する
4. Macieのジョブ完了イベントをCloudWatch Logsで監視し、メトリクスフィルターでSNS通知する
5. GuardDutyを使用してDynamoDB内のPIIを検出する

<details>
<summary>正解と解説</summary>

**正解: 1, 3**

- **Macie**: S3バケット内のデータからPIIや機密データを自動検出するサービス。DynamoDBのデータはまずS3にエクスポートする必要がある
- **EventBridge + SNS**: Macieのジョブ完了イベントをEventBridgeルールで捕捉し、SNSトピック経由でメール通知する標準的なパターン
- DynamoDB Streams + Lambda + Comprehendも技術的には可能だが、リアルタイム処理となり「月次スキャン」の要件に対して過剰で運用コストが高い
- GuardDutyはセキュリティ脅威の検出サービスであり、PII検出には使えない

**覚えるポイント:** S3上のPII検出 → Macie。イベント通知 → EventBridge + SNS
</details>
